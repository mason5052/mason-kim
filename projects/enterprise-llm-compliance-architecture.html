TL;DR

  • 9-step request pipeline: Identity -> Input Gate -> Classification -> Policy -> Routing -> Redactor -> LLM -> Output Gate -> Audit
  • Hybrid sensitivity classifier fusing keyword + semantic axes with fail-closed upgrades and a kill switch
  • 3-axis access policy: Entity x Domain x Role-Level with cross-domain rules and PII drop-fields
  • Local-first routing with explicit user-consent escalation to a cloud LLM (vendor-agnostic) and full conversation continuity
  • Append-only audit with 7-year S3 Object Lock retention, OpenSearch warm index, and DynamoDB hot tier
  • Open-source companion repo with 6 docs, 4 architecture diagrams (Mermaid), 4 worked examples (policy YAML, IAM, request traces, classifier outputs)

The Problem

Enterprises deploying LLM assistants on internal data face a recurring failure mode: pipelines trust the model to enforce access controls. The model is trained to be helpful, not to be a security boundary. A senior employee's correctly-scoped query and a junior employee's out-of-scope query look identical to the model. The gap is filled by surrounding the LLM with code-enforced gates -- a compliance pipeline that runs before and after the model on every turn.

This project is the reference architecture for that pipeline. It is vendor-agnostic, fully synthetic, and open-source. The repository captures the design decisions, trade-offs, and worked examples needed for a security or platform team to stand up an equivalent system.

Each step has a single, narrow responsibility. The pipeline is fail-closed: any unhandled error short-circuits to DENY rather than ALLOW. Steps cannot de-escalate -- a step can raise sensitivity but never lower it.

Hybrid Sensitivity Classification

Step 3 fuses two independent classification axes:

AxisEngineStrengthWeakness
KeywordVendored YAML score table (deterministic)Fast, cheap, auditable, rule-versionableMisses paraphrase and obfuscation
SemanticLocal LLM with strict JSON-only promptCatches paraphrase, intent, indirect signalsSlower, costs tokens, can answer UNKNOWN

Fusion rule: level = MAX(keyword_level, semantic_level). Fail-closed upgrade: if semantic returns UNKNOWN and keyword score >= 30, promote to SECRET regardless of either individual axis. Kill switch: setting SEMANTIC_CLASSIFIER_ENABLED=false reverts to keyword-only mode without changing pipeline shape.

3-Axis Access Policy

Authorization is computed across three independent axes with a fully-deterministic decision table:

AxisValuesSource
EntityCORP, SUB-A, SUB-B, SUB-C, JV-XHRIS / org chart
DomainFIN, HR, SALES, SCM, ENG, OPS, LEGALDepartment mapping
Role LevelSTAFF (1), LEAD (2), DEPT (3), EXEC (4)HRIS role tier

Rules combine the resolved query's sensitivity, target entity, and target domain with the requester's scope and role-level. Cross-domain joins (e.g., HR x SALES) take the maximum floor of all involved domains and apply additional drop-field rules to strip PII before the request reaches the LLM. The policy engine emits a fully-decomposed decision record into the audit log -- no opaque ALLOW/DENY tokens.

Local-First Routing with Explicit Consent

Most queries route to a self-hosted LLM (private VPC, no egress). When the local model fails -- tool-loop, vLLM 5xx, malformed output, or unreachable endpoint -- the router does not silently escalate. Instead:

  1. Sensitivity is re-classified on the failed query.
  2. SECRET-tier queries surface a localized failure message with the concrete reason and never offer external escalation.
  3. INTERNAL/CONFIDENTIAL queries surface a 3-button consent card: Send to external AI / Cancel / Ask differently.
  4. If the user clicks send, conversation history is sanitized, PII is re-redacted, the cloud LLM receives a stripped request, and the response is filtered by the output gate before joining the conversation.

The vendor-facing UI string uses generic vendor + model display names (e.g., "Claude Sonnet 4.5 via Anthropic"). The infrastructure-facing vocabulary -- internal service names, vLLM, internal IPs -- is deliberately absent from user surfaces.

Audit and Observability

The audit sink is the system of record. Every request emits a single ULID-keyed audit envelope into three tiers:

TierBacking StoreRetentionUse Case
HotDynamoDB audit-recent7 days TTLOperator triage, real-time queries
WarmOpenSearch index90 daysInvestigations, compliance queries, dashboards
ColdS3 with Object Lock7 years (immutable)Regulatory audit, post-incident forensics

The S3 cold tier is write-once-read-many. Object Lock + bucket-level deny on s3:DeleteObject + versioning prevents tampering even by privileged operators. A separate audit-ingestion Lambda owns the write path; the gateway Lambda has no S3 delete permissions.
