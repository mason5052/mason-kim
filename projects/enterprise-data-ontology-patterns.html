Why an Ontology

An LLM gateway can run flawless authorization, classification, and redaction -- and still produce wrong answers if the underlying data is shaped as ad-hoc tables. "Show me Q3 pipeline for SUB-A" only has a single decidable answer when "pipeline" is a registered metric, "Q3" resolves to a specific fiscal calendar, and "SUB-A" is a known entity with a known scope. Without that structure, the LLM hallucinates plausible numbers from whatever rows it can see.

This repo captures the structured-knowledge layer that makes the compliance pipeline decidable. It is the natural complement to the Enterprise LLM Compliance Architecture: the policy engine cannot enforce a domain floor without registered domains, and the audit log cannot reconstruct a decision without registered metric IDs.

Domain Decomposition

Seven business domains, each with a single owning team role and a sensitivity floor (the minimum level any metric in that domain can carry):

SCMINTERNALinventory, shipment, vendor spend
ENGINTERNALdeploy frequency, MTTR, error budget

LEGALCONFIDENTIALcontracts, recall events, NDAs

Entity and Axis Modeling

Five entity codes (organizational structure) combined with six first-class axes (analytical dimensions). Every metric declares its axes explicitly -- no implicit defaults that hide drift.

AxisDefaultNotes
EntitySUB-ACORP / SUB-A / SUB-B / SUB-C / JV-X. JV inherits parent's domain rule plus one role-level.
Timequarter, fiscal calendarValid grains: day / week / month / quarter / year
CurrencyUSD, spot_at_txnFX method declared per metric -- spot, period_avg, period_end
CustomernonePII axis, volatile -- triggers Redactor and CONFIDENTIAL floor
ProductfamilyRollup levels: sku / family / category / all
RegionnoneRollup levels: country / subregion / region / global

Naming convention: {domain}.{concept}.{qualifier(s)}.{unit_or_method}

Lifecycle: draft -> approved -> deprecated -> retired with a 90-day transition window. Deprecated metrics keep resolving but emit warnings; retired metrics return a deny with the replacement ID.

Cross-domain reconciliation: a metric in one domain can declare a cross_domain_link to another, with a numeric tolerance. Example: sales.bookings.gross.usd_period_avg reconciles to fin.revenue.gross.usd_period_avg within 0.5%. Out-of-tolerance reconciliations surface as audit anomalies, not silent drift.

Worked Examples: SALES and SCM

SALES models the full lead-to-cash entity graph: Lead -> Account -> Contact (PII), Opportunity -> Deal -> Contract -> LineItem. Stages are a state machine with default close probabilities (qualified 10%, discovery 25%, proposal 50%, negotiation 75%, closed_won 100%). The repo includes 12 fully-spec'd metrics in YAML covering pipeline (count / unweighted USD / weighted USD), bookings (gross / net), revenue (gross / ARR / NRR), and customer counts (acquisition / churn / list-with-contact with PII redaction).

SCM models the supply-chain graph: SKU (NPI -> GA -> EOL -> EOSL), Lot (in_qa -> released -> shipped -> consumed/expired/recalled), Shipment (booked -> in_transit -> delivered/exception). The repo includes 14 fully-spec'd metrics covering inventory (units / USD-at-cost / expiring / recalled / DIO), shipment (in-transit / OTD / exception), lane (lead-time / cost-per-unit), and vendor (spend / OTD / defect-rate / concentration). Vendor concentration above 40% triggers a SECRET-tier flag and a quarterly OPS+LEGAL review -- a worked example of a numeric threshold escalating sensitivity.
